# 노노무라 병원 사람들 — New 3DS 네이티브 포팅

DOS 게임(사과나무팀 한글판)을 **자체 x86 에뮬레이터**로 3DS에서 직접 실행하는 홈브루입니다.
(DOSBox가 아니라 이 프로젝트 안에 들어 있는 CPU/VGA/EMS/XMS/마우스/OPL 음악 에뮬레이터입니다.)

- **상단 화면**: 게임 화면 (400x240 화면 가득 확대로 고정, 예전 "원본 4:3" 선택은 삭제)
- **하단 화면**: 대사 텍스트를 다시 배치해서 표시 (게임이 글자를 그릴 때 글리프를 가로채서 확대). 게임이 폭에 맞춰 꺾어 둔 줄은 한 문단으로 이어 붙여 단어 단위로 다시 줄바꿈합니다.
- **상단 화면 3D 효과**: 3DS 옆면의 **3D 슬라이더를 올리면** 상단 그림이 입체로 보입니다. 일시정지 메뉴의 `상단 3D 효과`에서 끔/약/중(기본)/강/최강을(눈 사이 간격: 캐릭터 6/12/18/24px, 이전 "강"이 지금 "중"), `상단 3D 방식`에서 스타일을 고릅니다. 실제 깊이는 슬라이더 위치에 비례하고, 슬라이더 0이거나 `끔`이면 평소처럼 2D입니다(설정 `s3d`, `s3dm`).
  - **캐릭터+테두리**(기본, `s3dm=0`): 배경은 화면 표면에 그대로 두고 **캐릭터는 가장 앞으로, 그림 둘레의 장식 테두리는 그 사이로** 튀어나옵니다. 이 엔진은 배경(과 전체화면 이벤트 CG)을 한 루틴으로, 캐릭터를 다른 루틴(SILV1.COM 의 IP 1D00~1D7F, 사각형 블릿)으로 그리고, 눈 깜박임·입 움직임 같은 얼굴 부분 갱신은 또 다른 루틴(IP 2980~29AF, 플레인별 합성 루프)으로 얼굴 위에 덧씌우기 때문에(이 둘 다 캐릭터 쓰기로 취급, 안 그러면 얼굴 사각형이 배경으로 분류되어 3D에서 몸과 따로 놉니다), 에뮬레이터가 캐릭터 블릿을 제외한 화면 사본(`VGA.bgplane`, `core/vga.c` 의 `vga_write`)을 따로 유지합니다. 두 화면을 같은 방식으로 그려 비교하면 캐릭터 마스크가 나오고(`char_layer`, 작은 구멍은 닫기 연산으로 메움), 캐릭터를 좌/우 눈에서 반대 방향으로 밀어 합성합니다(`make_eye_char`). 캐릭터 뒤 배경은 사본에 온전히 있으므로 빈 틈이 생기지 않습니다. 테두리 모양은 모든 장면에서 같으므로 `ctr/source/frameshape.h`(안쪽 경계선, `tools/gen_frameshape.py` 가 여러 장면 화면을 비교해 생성)로 기술하고, 같은 확대 함수로 마스크를 만든 뒤(`frame_masks`) 테두리를 캐릭터보다 덜 튀어나오게 밀어 합성합니다. 테두리 안쪽에 드러나는 부분은 그림을 연장해 채웁니다(`build_bgx`). 캐릭터가 없거나(마스크 0.3% 미만) 전체화면 그림(70% 초과)이면 캐릭터는 평평하게(테두리만 입체) 표시하고, 대화창 띠(상단에 표시하는 경우)는 항상 화면 표면에 둡니다. 대화창을 숨긴 "꽉 채움" 확대에서는 테두리가 대부분 잘려 나가 있어 테두리 효과가 거의 보이지 않습니다(`상단 그림` 설정을 `늘림`/`비율 유지`로 하면 보임).
  - **캐릭터만**(`s3dm=2`): 위와 같지만 테두리는 평평하게 둡니다.
  - **화면 전체**(`s3dm=1`): 그림이 비스듬히 누운 면처럼 아래쪽은 화면 표면, 위쪽은 안쪽으로 들어가고, 둘레 프레임이 앞으로 튀어나옵니다(`make_eye`).
- 대화창이 떠 있는 동안 **상단 화면에는 그림만** 크게 표시하고(대화창 띠는 숨김) 글자는 하단 화면에서만 보입니다. 일시정지 메뉴의 `상단 대화창`에서 숨김/표시 전환 가능(설정은 `win_hide`).
- 그림만 보일 때의 확대 방식은 `상단 그림 (대화창 없음)`에서 선택: **꽉 채움**(기본: 그림 테두리를 잘라내고 400x240 화면 전체를 채움, 세로로 약간 늘어남) / **늘림**(테두리 포함 전체를 화면에 꽉 차게 늘림) (예전 "비율 유지" 선택은 삭제, 저장된 값은 무시). 설정은 `pic_mode`.
- 하단 화면은 대사가 없을 때 아무 글자도 표시하지 않습니다.
- **선택지(분기 메뉴), 세이브/로드 슬롯 목록**도 하단 화면에 크게 표시되고, 선택된 항목은 흰 막대로 강조되며, 항목 앞의 ●는 강조될 때(마우스 포인터가 ●를 덮고 있어도) 사라지지 않고 유지됩니다.
- 하단 글자 크기는 "아주 작게"(1배) 하나로 고정입니다(예전 `text_size` 설정은 무시). 줄 간격은 20px, 선택지 등 서로 다른 줄 사이에는 4px을 더 둡니다(`core/textcap.c` 의 `LINEH_BASE`, `LINE_GAP`). 다른 설정은 `nono_cfg.txt`에 저장됩니다.
- **메뉴·안내 문구는 모두 한글**입니다(일시정지 메뉴, 시작/오류 화면). 3DS에는 한글 글꼴이 없어서 `tools/gen_kfont.py`가 Noto Sans CJK KR(SIL OFL)에서 필요한 글자만 뽑아 `ctr/source/kfont.h`로 내장합니다. 문구를 추가·수정했다면 `python3 tools/gen_kfont.py`를 다시 실행하세요(Pillow 필요, 결과 파일은 저장소에 포함돼 있어 빌드에는 필요 없음).
- **음악**: OPL(FM) 칩을 본래 속도(49716 Hz)로 합성한 뒤 고품질 필터로 3DS DSP 기본 출력 속도(32728 Hz)로 변환합니다. (낮은 속도로 바로 합성하면 높은 소리가 접혀 들어와 지직거리는 소리가 납니다.) 합성 결과는 Nuked-OPL3(정확한 OPL 에뮬레이터)와 같은 연주 데이터로 비교해 음색(스펙트럼)이 1 dB 안팎으로 일치함을 확인했습니다.
- **소리 끊김 방지**: 에뮬레이션을 실제 시간보다 0.4초 앞서 돌려 그만큼의 소리를 항상 DSP에 쌓아 둡니다(화면 처리·저장이 잠깐 느려져도 음악이 끊기지 않음). 쌓인 양이 목표와 어긋나면(3DS 시계와 소리 칩 시계의 미세한 차이 등) 게임을 최대 ±3%만 느리게/빠르게 돌려 목표로 되돌리고(음높이는 그대로), 그래도 소리가 마르면 쌓아 두는 양을 0.1초씩 최대 0.9초까지 늘렸다가 조용한 동안 서서히 줄입니다. **소리를 최우선으로 한 진행 방식**: 무거운 장면(오프닝·화면 전환)에서는 상단 그림 갱신이 한 프레임 시간의 상당 부분을 써서, 예전에는 에뮬레이션에 프레임당 12ms만 주다 보니 게임이 실시간을 못 따라가 소리가 모자랐습니다(프레임 시간은 짧은데 끊김만 쌓이던 원인). 이제 게임이 뒤처졌거나 쌓인 소리가 목표의 85% 아래면 에뮬레이션에 최대 4프레임까지 주고, 쌓인 소리가 50% 아래면 상단/하단 그림 갱신을 잠시 줄이며, 3프레임 이상 연속으로 뒤처지면 에뮬레이션 CPU 속도(ips)를 곧바로 8%씩 낮춥니다(게임은 조금 느려져도 음악은 실시간 유지; 한가해지면 1초마다 6%씩 복구). 끊긴 뒤 다시 재생할 때는 목표량의 60%가 쌓일 때까지 기다립니다. PC 시험(test/stub3ds의 STUB_COST 비용 모델, 3DS가 느린 경우를 가정)에서 오프닝~6분 동안 끊김 6~13회 → 0~2회로 줄었습니다. **음악이 지직거리던 진짜 원인(OPL 주소 래치)**: 이 게임의 음악 드라이버(MUSICV.COM)는 OPL3 모드(0x105=1)에 4-오퍼레이터 음 6개(0x104=0x3F)를 쓰는데, 두 번째 레지스터 배열(음 3개)에는 주소를 0x38A로 보내면서 데이터는 항상 0x389로 보냅니다. 실제 YMF262는 주소 래치가 하나이고 데이터 쓰기는 A1과 무관하게 직전에 지정한 배열·레지스터에 들어가므로(데이터시트 'data write mode: A1 = don't care') 정상 동작합니다. 그런데 에뮬레이터가 배열마다 주소를 따로 들고 있어서 두 번째 배열용 데이터가 첫 번째 배열의 마지막 레지스터(B2 등)에 계속 덮어써졌고, 한 음 높이/건반이 틱마다 5~6번씩 뒤죽박죽이 되어 소리가 찌그러졌습니다. `core/opl.c`의 `opl_write`를 래치 하나(배열 번호는 주소 쓰기 때만 정함)로 고쳤습니다. 이제 음 6개가 모두 제대로 울려 소리가 더 풍부하고(합성 부하도 약 2.2배: PC 기준 오디오 1초당 4.5ms → 10ms), OPL3 스테레오 패닝도 그대로 출력됩니다. `host/run.c`의 OPLTRACE는 MUSICV 초기화(OPL3·4-op 설정) 쓰기까지 기록하도록 바꿨습니다. 이 때문에 앞서 '합성이 기준 구현과 같다'는 비교는 같은 잘못된 기록으로 한 것이었고, 고친 기록으로 다시 비교해도 파형 상관 0.96~0.99(리샘플러 지연 6샘플 보정 후)로 일치합니다. 일시정지 메뉴의 `소리 시험`은 깨끗한 음 7개에 이어 PC에서 만든 게임 음악 샘플 6초(`ctr/source/musicsample.h`, 고친 기록 기반)를 같은 경로로 재생합니다. 합성 소리는 기준 구현(Nuked-OPL3)과 같은 레지스터 기록으로 비교해 대역별 에너지가 1~3dB 안에서 일치하고(클릭/알리아싱 없음) 리듬 모드는 이 게임 음악에서 쓰이지 않음을 확인했습니다. 출력은 너무 작아(rms ≈ -35dBFS) 3DS 음량을 높여야 했으므로 합성 이득을 1.5배 올렸습니다(음 6개가 모두 울리는 지금은 rms ≈ -19dBFS, 최대 ≈ -3.5dBFS로 부드러운 리미터 26000 아래). 게임 중 DSP에는 소리 시험과 같은 1024샘플 단위 버퍼로 묶어서 보냅니다(DSP가 거의 비는 때만 짧은 버퍼).
소리 대기 칸(96개)과 합성기 버퍼(2초)는 이 양보다 충분히 크게 잡아서, 예전처럼 칸이 가득 차 소리를 버리는 일이 없습니다(이전 버전은 칸 32개≈0.5초라 쌓아 두는 양을 늘릴수록 오히려 소리를 잘라 먹었습니다). 한 번 느려진 초를 "만성 저속"으로 오인해 소리를 늘려 재생하던 동작은 4초 이상 계속될 때만 작동하도록 바꿨습니다. SELECT 오버레이에 `lead`(현재 목표 ms), `frm max/>100/>250`(프레임 지연), `adj`(속도 보정), `worst`(가장 느렸던 프레임이 에뮬레이션/소리/상단/하단/수직동기 대기 중 어디서 시간을 썼는지 ms), `avg`(최근 1초 평균 프레임 시간 ms: 에뮬레이션/소리/상단/하단/수직동기 대기, `lag`=에뮬레이션이 실시간을 못 따라간 프레임 비율), `dos max`(가장 오래 걸린 DOS 호출과 50ms 넘은 횟수)가 표시됩니다. 게임 데이터 파일(SILK*.DAT, SAGWA.* 등)은 시작할 때 RAM에 올려서 게임 중 SD 카드 읽기 지연이 없습니다(시작할 때 "불러오는 중..."이 조금 길어집니다).
- 일시정지 메뉴의 `소리 시험`은 에뮬레이터와 무관하게 음계 톤을 재생합니다. 톤은 깨끗한데 게임 음악만 깨진다면 에뮬레이션 쪽, 톤도 깨진다면 3DS 출력 쪽 문제입니다.

## 설치 (SD 카드)

```
SD:/3ds/nonomura.3dsx          ← 빌드된 홈브루 파일
SD:/3ds/nonomura/              ← 게임 파일 전부 (SILV1.COM, SILV.EXE, MUSICV.COM, SAGWA.*, FLAG*, SILK*.DAT ...)
```

세이브(FLAG0~8, SILK*.DAT)는 게임 폴더(`SD:/3ds/nonomura/`)에 그대로 저장됩니다.
문제가 생기면 같은 폴더의 `nono_log.txt`를 확인하세요 (속도/오류 기록).

| START | 일시정지 메뉴 (대화창 숨김, 그림 확대 방식, 상단 3D 효과, CPU 속도, 마우스 속도, 소리 시험, 게임 종료) |

## 빌드

GitHub Actions(`.github/workflows/build.yml`)가 `ctr/nonomura.3dsx`를 만들어 줍니다.
로컬 빌드: devkitARM + libctru 설치 후 `make -C ctr`.

## 구조

- `core/` — x86(386 실모드) 인터프리터, DOS/BIOS/EMS/XMS/마우스 HLE, VGA, OPL2/OPL3, 대사 캡처(textcap)
- `ctr/` — 3DS 프런트엔드 (화면, 입력, 오디오, 메뉴)
- `host/`, `test/` — PC에서 돌려 보는 테스트 러너
- `tools/` — 개발용 스크립트(`gen_kfont.py`: 메뉴용 한글 글꼴 생성)

## 알려진 한계

- 게임 속도는 실제 시간(시스템 시계)에 맞춰 돌리고, 대기 구간(키 입력/타이머 대기)은 에뮬레이션을 건너뛰어 CPU를 아낍니다. 소리는 버리지 않고 쌓아 두었다가 재생합니다. 메뉴 하단에 Speed(%)와 CPU 사용률이 표시됩니다.
- 실기기 테스트는 계속 진행 중입니다. 속도가 부족하면 에뮬레이션 CPU 속도를 자동으로 낮춰 실시간에 맞춥니다(게임이 약간 느려질 수 있음).
- 하단 대사 확대는 이 게임 엔진(SILV)의 글자 그리기 루틴을 기준으로 합니다.
